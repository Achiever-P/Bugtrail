Project Frame · STAR

Why This, Why Now

🔍 SITUATION

Software teams find defects at every stage of the SDLC, but most still track them through spreadsheets, chat threads, or ad-hoc emails — nothing that survives a handoff or an audit.

🎯 OBJECTIVE

Build a system that gives every bug a fixed identity, a defined lifecycle, and a clear owner — from the moment it's reported to the moment it's verified closed.

⚡ ACTION

Design and build BugTrail: a MERN application enforcing a server-side status workflow, role-based permissions, and a full audit trail for every change.

✅ RESULT

A working full-stack system with projects, Kanban board, assignment, comments, notifications, file attachments, sprint management, and activity logs — seeded and ready for a live team.

Aim & Objectives

What BugTrail Sets Out to Do

AIM: To design and implement a full-stack bug tracking system that enforces a disciplined resolution workflow across the SDLC — replacing ad-hoc bug management with a structured, auditable process any team can run.
🆔

Objective 1

Give every bug a unique identity (AF-1, MOB-3) and a fixed lifecycle — instead of a free-text status field anyone can edit.

🛡️

Objective 2

Enforce role-based permissions on the server, not just hide buttons in the interface. Every API endpoint validates the user's role.

📋

Objective 3

Record a complete audit trail for every assignment, status change, and priority edit — with who, when, and before/after values.

📊

Objective 4

Surface project health through live dashboards with real-time charts — instead of manual status meetings.

05 / 24
Proposed Solution

Four Mechanisms, One Disciplined Workflow

STATE MACHINE

Server-Enforced Status Workflow

Bugs move open → in progress → in review → resolved → closed. Invalid jumps are rejected by the API itself, not just discouraged in the interface. A constant TRANSITIONS map defines every valid move.

RBAC

Role-Based Access Control

Admin, Developer, Tester, and Reporter each get a distinct set of permitted actions, checked in middleware on every single request. The authorize() middleware gates 35+ endpoints.

AUDIT LOG

Full Activity Trail

Every status change, assignment, and priority edit writes a log entry recording who acted, when, and the before/after value. 10 tracked action types across 7 MongoDB collections.

DASHBOARD

Live Project Visibility

Aggregate queries turn raw bug documents into status and priority breakdowns — 8 stat cards and 6 interactive charts. No manual standup required to know where things stand.

Database Design

7 MongoDB Collections

👤 User

name, email, password (hashed), role (4 types), avatarInitials (auto-generated), isActive

📁 Project

name, key (unique, uppercase), description, lead, members[], isArchived, bugSequence (atomic counter)

🐛 Bug

bugId, title, description, steps, expected/actual result, status, priority, severity, labels[], dueDate, attachments[], watchers[], sprint ref

💬 Comment

bug ref, author ref, text, timestamps. Authors can edit/delete own; admins can moderate.

📋 ActivityLog

bug ref, actor ref, action (10 types), fromValue, toValue. Immutable audit trail.

🔔 Notification

recipient, type (7 types), title, message, bug/project/actor refs, isRead. Auto-created on key events.

🏃 Sprint

name, project ref, start/end dates, status (planning/active/completed), bugs[], createdBy.

Key Design Decision: Bug IDs are generated atomically using MongoDB's $inc operator on the project's bugSequence field — preventing race conditions under concurrent requests. 5 database indexes on the Bug collection ensure query performance.

Security

Security Measures

🔑 Authentication

bcrypt hashing (10 rounds), JWT with 7-day expiry, password field select: false — never returned in responses

⏱️ Rate Limiting

20 requests per 15 minutes on login/register endpoints. Prevents brute force attacks.

🛡️ Helmet

Sets Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, and other security headers automatically.

✅ Input Validation

Every controller validates required fields, ObjectId format, and enum values before any database operation.

🔐 Admin Safety

Cannot remove last admin, cannot deactivate self, public registration blocked from creating admin accounts.

📁 Upload Security

MIME type allowlist, file size limits, UUID filenames, cross-origin resource policy for file serving.

Challenges

Technical Challenges & Solutions

🏎️ Race Condition in Bug ID Generation

Problem: Two concurrent requests could read the same sequence number and create duplicate IDs.

Solution: Used MongoDB's atomic $inc with findByIdAndUpdate — increment and return in one atomic operation.

🔀 State Machine Enforcement

Problem: Kanban drag-and-drop could bypass workflow rules if only validated on frontend.

Solution: Duplicated TRANSITIONS map on both frontend (for UX feedback) and backend (for enforcement). Backend is the source of truth.

📍 Notification Dropdown Positioning

Problem: Dropdown clipped by sidebar's overflow: hidden.

Solution: Used React's createPortal to render dropdown into document.body with viewport-relative positioning.

🔐 Admin Lock-Out Prevention

Problem: Admin could accidentally remove all admin accounts.

Solution: Server counts active admins before role change/deactivation. Blocks if it would leave zero admins.

Future Scope

Limitations & Future Scope

⚠️ Current Limitations

  • No real-time updates — uses polling (30s intervals) instead of WebSockets
  • No email notifications — only in-app; SMTP architecture exists but not implemented
  • No automated test suite — manual QA only
  • Single-file uploads — no batch upload support
  • Web-only — no native mobile app

🚀 Future Scope

  • WebSocket integration — Socket.io for real-time Kanban collaboration
  • Email notifications — Nodemailer with configurable SMTP
  • GitHub/GitLab integration — link commits to bug IDs
  • AI duplicate detection — text similarity to flag duplicates
  • Custom workflow templates — team-defined state machines
  • Docker + CI/CD — containerized deployment
