1. Introduction & Project Overview

BugTrail is a full-stack, production-ready bug tracking and resolution system built with the MERN stack. It enables software development teams to report, track, assign, and resolve bugs through a structured workflow with complete audit trails, real-time notifications, and a visual Kanban board.

1.1 Problem Statement

Software development teams require a centralized system to efficiently track, prioritize, and manage software defects throughout the development lifecycle. Manual tracking through spreadsheets or email leads to lost bugs, unclear ownership, and lack of accountability. BugTrail addresses this by providing a modern, role-based bug management platform.

1.2 Key Features

🔐

Role-Based Access Control

Four distinct roles (Admin, Developer, Tester, Reporter) with granular server-enforced permissions on every API endpoint.

🐛

Complete Bug Lifecycle

State machine-driven workflow with 6 statuses, validated transitions, and automatic audit logging at every step.

📋

Kanban Board

Visual drag-and-drop board with real-time status updates, transition validation, and assignee filtering.

🔔

In-App Notifications

Automatic notifications for assignments, status changes, comments, and due dates — persisted in MongoDB.

📊

Dashboard & Analytics

8 stat cards and 6 interactive Recharts visualizations covering status, priority, severity, and trends.

📎

File Attachments

Upload screenshots, documents, and reproduction files with Multer. Type/size validation and secure access control.

🏃

Sprint Management

Create sprints with date ranges, assign bugs, track progress, and manage sprint lifecycle (planning → active → completed).

💬

Comments & Collaboration

Add, edit, and delete comments on bugs. Chronological display with author info and role badges.

1.3 Objectives

  • Provide a centralized platform for bug reporting, tracking, and resolution
  • Implement role-based access control with server-side enforcement
  • Enable visual workflow management through a Kanban board
  • Maintain a complete audit trail of all bug-related actions
  • Deliver a responsive, professional dark-themed UI
  • Ensure data integrity with backend validation and atomic operations

3.2 Request-Response Flow

How a typical API request flows through the system:
  1. User Action → React component triggers an event (button click, form submit)
  2. Axios Call → api.get/post/patch/delete() sends HTTP request to /api/*
  3. Axios Interceptor → Automatically attaches JWT token from localStorage as Authorization: Bearer <token>
  4. Vite Proxy → Forwards /api/* requests to http://localhost:5000
  5. Express Middleware Chain:
    • helmet() → Sets security headers
    • cors() → Validates origin
    • express.json() → Parses JSON body
    • rateLimit() → Throttles auth endpoints (20 req / 15 min)
    • protect → Verifies JWT, loads User from DB, attaches to req.user
    • authorize() → Checks role-based permissions
  6. Controller → Executes business logic, queries MongoDB via Mongoose
  7. Response → JSON response sent back to React
  8. React State → Component updates UI with new data

5.2 User Model

Field Type Constraints Description
name String Required, trimmed Full name
email String Required, unique, lowercase Login email
password String Required, min 6 chars, select: false Bcrypt hashed (10 rounds)
role String Enum: admin, developer, tester, reporter Default: reporter
avatarInitials String Auto-generated on save Two-letter initials from name
isActive Boolean Default: true Account activation status
Pre-save Hooks: Two Mongoose pre-save hooks run automatically: (1) hash password if modified, (2) generate avatarInitials from name. The toSafeObject() method strips the password before sending to clients.

5.3 Project Model

Field Type Constraints Description
name String Required Project name
key String Required, unique, uppercase Short key (e.g., "BUG", "APP") for bug IDs
description String Optional Project description
lead ObjectId → User Required Project lead reference
members [ObjectId → User] Array Project team members
isArchived Boolean Default: false Archive status
bugSequence Number Default: 0 Atomic counter for bug ID generation
Atomic Bug IDs: When a bug is created, bugSequence is incremented using findByIdAndUpdate($inc: { bugSequence: 1 }). This ensures unique, sequential bug IDs (e.g., APP-1, APP-2) even under concurrent requests — no race conditions.

6. Authentication & Authorization

6.1 Authentication Flow

Login Flow:

1. User submits email + password on /login page
2. POST /api/auth/login → find user by email, compare bcrypt hash
3. If valid → generate JWT with { id: user._id }, expires in 7 days
4. Return { token, user } → stored in localStorage (bt_token, bt_user)
5. Axios interceptor attaches Authorization: Bearer <token> to every request
6. On page refresh → AuthContext calls GET /api/auth/me to re-validate token

Registration Flow:

1. User fills name, email, password, role
2. POST /api/auth/register → validates input, hashes password
3. Security: Public registration CANNOT create admin accounts — role forced to reporter/developer/tester
4. Auto-generates avatarInitials from name

Backend Enforcement: The TRANSITIONS constant in bugController.js strictly defines allowed transitions. Any attempt to make an invalid transition (e.g., Open → Resolved) returns a 400 Bad Request with a descriptive error message. The Kanban board's drag-and-drop also validates transitions client-side before making the API call.

8.3 State Machine Implementation

const TRANSITIONS = {
  open:        ["in_progress", "closed"],
  in_progress: ["in_review", "open", "closed"],
  in_review:   ["resolved", "in_progress"],
  resolved:    ["closed", "reopened"],
  closed:      ["reopened"],
  reopened:    ["in_progress", "closed"],
};

// In changeStatus controller:
const allowed = TRANSITIONS[bug.status] || [];
if (!allowed.includes(newStatus)) {
  return res.status(400).json({ message: `Cannot move from '${bug.status}' to '${newStatus}'` });
}

9.3 State Management

BugTrail uses two React Contexts for global state:

  • AuthContext — Manages user authentication state. Stores JWT in localStorage. On mount, calls /api/auth/me to re-validate the token. Provides login(), register(), logout() functions and the user object to all components.
  • ToastContext — Provides toast.success(), toast.error(), toast.info() for non-intrusive feedback messages. Toast notifications auto-dismiss after a few seconds.

11.3 How Drag-and-Drop Works

  1. Drag Start: HTML5 Drag API — draggable attribute + onDragStart event stores the bug object
  2. Visual Feedback:
    • Blue dashed border = valid drop target (allowed transition)
    • Red dashed border = invalid drop target (transition not allowed)
  3. Client-side Validation: Before API call, checks the TRANSITIONS map
  4. API Call: PATCH /api/bugs/:id/status with new status
  5. Server Validation: Backend re-validates the transition (never trust client)
  6. Board Refresh: On success, reloads all bugs from API
  7. Error Handling: On failure, shows toast error and reverts visually

11.4 Bug Card Information

Each card on the board displays: Bug ID (e.g., APP-3), title, priority badge, severity tag, and assigned developer avatar.

12. File Attachments

12.1 Upload Pipeline

1. User clicks "Upload File" on Bug Detail page → hidden <input type="file"> opens
2. File is sent as multipart/form-data to POST /api/bugs/:id/attachments
3. Multer middleware processes the upload:
   a. File filter: Validates MIME type against allowlist
   b. Size limit: Max 5 MB (configurable via MAX_FILE_SIZE env var)
   c. Storage: Saved to uploads/ with UUID filename to prevent collisions
4. Attachment metadata (filename, original name, MIME type, size, URL, uploader) is pushed to the bug's attachments subdocument array
5. Files are served statically via express.static('/uploads')

12.2 Allowed File Types

Images (JPEG, PNG, GIF, WebP, SVG), Documents (PDF, Word, Excel), Data (JSON, CSV, TXT), Archives (ZIP), Video (MP4, WebM)

12.3 Security

  • Only the uploader or an admin can remove an attachment
  • File is deleted from disk when removed from the bug
  • Binary files are NOT stored in MongoDB — only metadata references
  • Helmet's crossOriginResourcePolicy is set to "cross-origin" for file serving

16. Security Measures

Measure Implementation
Password Hashing bcryptjs with 10 salt rounds. Passwords are never stored in plaintext.
JWT Authentication Stateless tokens with configurable expiry (default 7 days). Secret stored in JWT_SECRET env var.
Password Hidden select: false on User schema — password never returned in API responses.
Rate Limiting 20 requests per 15 minutes on /api/auth/login and /api/auth/register.
Helmet Sets Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, and other security headers.
CORS Configurable origin via CLIENT_URL env var. Defaults to * in development.
Input Validation Every controller validates required fields, ObjectId format, enum values before database operations.
Role Authorization Server-side authorize() middleware checks user role on every protected endpoint.
Admin Protection Cannot remove the last admin. Cannot deactivate your own account. Public registration cannot create admins.
File Upload Security MIME type allowlist, file size limit, UUID filenames to prevent path traversal.
Account Deactivation Deactivated users cannot login. Auth middleware checks isActive on every request.
Payload Limits express.json({ limit: "10mb" }) prevents oversized request bodies.

19. Data Flow Diagrams

19.1 Bug Creation Flow

User fills Create Bug form
→ POST /api/bugs with title, description, project, priority, severity, labels, dueDate
→ protect middleware verifies JWT → req.user set
→ Controller: Project.findByIdAndUpdate($inc: { bugSequence: 1 }) (atomic)
→ Generate bugId = PROJECT_KEY-SEQUENCE (e.g., "APP-7")
→ Bug.create() with all fields, reporter = req.user._id, auto-watch reporter
→ ActivityLog.create() with action = "created"
→ If assignedTo provided → Notification.insertMany() to assignee
→ Return populated bug object to frontend
→ Frontend updates bug list / redirects to bug detail

19.2 Status Change Flow

User clicks status button or drags on Kanban
→ PATCH /api/bugs/:id/status with { status: "in_progress" }
→ protect middleware verifies JWT
→ Controller: Load bug from DB, check TRANSITIONS[bug.status]
→ If invalid → return 400 with descriptive error
→ If valid → update bug.status, set resolvedAt/closedAt if applicable
→ bug.save()
→ ActivityLog.create() with fromValue and toValue
→ Notification.insertMany() to watchers + assignee + reporter (minus actor)
→ Return updated bug
→ Frontend refreshes bug detail / Kanban board

19.3 Authentication Flow

Login: Submit email + password → POST /api/auth/login
→ Find user by email → bcrypt.compare() password hash
→ If valid + active → jwt.sign({ id }) → return { token, user }
→ Frontend stores in localStorage: bt_token, bt_user
→ AuthContext sets user state → app renders authenticated UI

Subsequent Requests: Axios interceptor reads bt_token
→ Adds Authorization: Bearer <token> header
→ Vite proxy forwards /api/* to Express
→ protect middleware decodes + verifies JWT → loads user from DB

Page Refresh: AuthContext.useEffect → GET /api/auth/me
→ Validates token still valid + user still active
→ If invalid → clears localStorage → redirect to login
